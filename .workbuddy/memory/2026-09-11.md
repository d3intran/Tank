# 2026-09-11

## M2 重生占有链路 bug —— 根因定位并修复（结案）

`docs/tank-ffa-plan.md` 里挂了一天的"M2 未结案问题"（神秘 UnPossession / 主机坦克被传送 /
两辆坦克堆叠 / 补发循环）找到根因了，**不需要原文设想的"死亡重置模型"**。

### 根因

`ATankPawn` 构造函数里的 `AutoPossessPlayer = EAutoReceiveInput::Player0`。

- `APawn::PreInitializeComponents()`（Pawn.cpp:116）在 `AutoPossessPlayer != Disabled && GetNetMode() != NM_Client`
  时取 `GetPlayerController(this, Index)` 直接 `PC->Possess(this)`。**每次服务端 Spawn 坦克都会执行**。
- `AController::OnPossess()`（Controller.cpp:356）换成另一个 Pawn 前会先 `UnPossess()`。

所以"为客户端重生而 Spawn 坦克"必然把主机正在开的坦克就地 UnPossess → 孤儿。
孤儿没有 Controller → `ChoosePlayerStart` 的存活坦克统计漏掉它 → 新坦克按"离存活坦克最远"
选点正好叠在孤儿身上 = 堆叠症状。三个症状同一个根因。

### 修复

`TankPawn.cpp` 构造函数两行：
- `AutoPossessPlayer = EAutoReceiveInput::Disabled;`
- `AutoPossessAI = EAutoPossessAI::Disabled;`  ← **必须配套**

配套原因：`AutoPossessPlayer` 一旦 Disabled，`APawn::PostInitializeComponents` 就放开了
`AutoPossessPlayer == Disabled && AutoPossessAI != Disabled && GetController() == nullptr` 这条分支。
`APawn` 的 `AutoPossessAI` 默认 `PlacedInWorld`、`AIControllerClass` 默认 `/Script/AIModule.AIController`；
开局 `World->bStartup` 为真 → 出生被判成 PlacedInWorld → `SpawnDefaultController()` 生 AIController 抢占有。

安全性已验证：全 Content 扫描无任何 uasset/umap 引用 `TankPawn` 或序列化 `AutoPossessPlayer`，
不存在 Blueprint 子类覆盖构造函数默认值的可能；`DefaultPawnClass` 由 C++ 的 `ABattleGameMode` 提供。

### 同批修掉

- `TankHealth.h`：`IsDepleted()` 改为 `bDepleted || CurrentHealth <= 0`（`bDepleted` 不复制，
  客户端恒 false → 头顶血条不剔除阵亡坦克）
- `TankPawn.cpp`：`MoveForward` 逐帧 Log→Verbose（单局 1114 行刷屏）；`UnPossessed` 补 Frame/PendingKill
- `TankPawn.h/.cpp`：删除死状态 `CurrentPitchInput`（只声明+清零、从未赋值，Tick 里那段分支不可达）
- `TankPawn.cpp`：`Fire()` 加 `IsDepleted()` 早退（阵亡到销毁 0.2s 窗口内还能开火）

# 第二轮：又挖出两个真 bug（均已修复+重新编译链接）

## Bug 2：FFA 选点在重生时根本不会执行（`BattleGameMode`）

`AGameModeBase::Login` 会把首次出生点存进 `PlayerController->StartSpot`；而
`FindPlayerStart` 开头 `if (ShouldSpawnAtStartSpot(Player))` 默认实现是
`return Player->StartSpot != nullptr` → 直接返回首次出生点，**`ChoosePlayerStart` 永远走不到**。
`AGameMode` 并未覆盖它（已核对 GameMode.cpp）。所以「离所有存活坦克最远」的 FFA 选点是死代码，
所有重生都固定回最初出生点。这也解释了当时"改最远点后传送减少但未根治"——改动只在首次出生生效过。

**修复**：覆盖 `ShouldSpawnAtStartSpot` 返回 `false`。

## Bug 3：头顶血条投影判据写反（`BattleHUD`）

`UCanvas::Project`（Canvas.cpp:1890）的 Z 是**裁剪空间 NDC 深度**，且**只在点位于相机身后
（`V.W <= 0`）时才被夹成 0**（引擎注释 "if behind the screen, clamp depth to the screen"）。
`FPlane : public FVector`（`TPlane : public TVector`），`FVector resultVec(V)` 是切片拷贝取 (X,Y,Z)。
原判据 `Projected.Z == 0.0f` 语义反了：只有身后的坦克通过，正前方的坦克永远画不出头顶血条。
**修复**：改为 `Projected.Z > 0.0f`。

## 确认「不是」bug 的两处（省得以后重复怀疑）

- 炮弹 `BlockAllDynamic` **不会**穿地面/城墙。UE4 时代的"BlockAllDynamic 忽略静态"印象在 UE5 不成立：
  核对 `BaseEngine.ini` + `CollisionProfile.cpp` 后确认 BlockAll 与 BlockAllDynamic 的
  `CustomResponses` 都为空、共用同一份默认响应容器，**两者只差 ObjectType**。
  项目里补的 `ECC_GameTraceChannel1 → Block` 补的是自定义通道（自定义通道默认响应未必是 Block），补得对。
- `TankProjectile` 的伤害/销毁/击杀者归属链路无问题。

## 配置补充

`Config/DefaultEngine.ini` 加 `GlobalDefaultGameMode=/Script/Tank.BattleGameMode`
（CRLF 文件，用 Python 按字节改的，别用会改行尾的工具）。关卡 WorldSettings 的
`DefaultGameMode` 仍优先，当前地图行为不变；补它是为新建地图/打包不退回 `AGameModeBase`。

## 两个重要的认知修正（别再踩）

- **`PlayNumberOfClients=3` + ListenServer 是 3 个玩家总数**（1 server + 2 client = 3 个世界），
  不是 1+3=4。日志 `Player joined ... 当前 3 人` 与 `get_pie_worlds(False)` 返回 3 一致。
- **客户端世界里远端 Pawn 的 `Controller` 为 NONE 是正常的**：远端 PlayerController 不复制到客户端。
  孤儿判定**只能在服务端世界做**（唯一拥有多个 PC 的那个世界）。
  第一版 `pie_inspect.py` 就是栽在这，把 4 辆正常车误报成孤儿。

## 已确认是「PIE 退出清理」而非 bug 的 UnPossessed

`pie_stop.py` 结束 PIE 时日志会出现 5 条 `被 UnPossessed！Frame=607 PendingKill=0`，
但每条前一行都是 `LogWorld: BeginTearingDown for /Game/UEDPIE_N_Lv1-TankArena` +
`Window 'Tank Preview [NetMode: Client N]' being destroyed`，全部同一帧、伴随
`World NetDriver shutdown` / `HostClosedConnection`。这是正常拆卸。
**与原 bug 的区别**：原 bug 是随机单辆、游戏中、与别人死亡相关；这里是 3 辆同帧一起、退出时。
