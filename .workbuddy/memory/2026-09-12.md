### Bug2（FFA 选点）的决定性判别实验

前两次尝试失败/无判别力，记下来省得重踩：

1. 直接瞬移**客户端**坦克聚堆 → **无效**：客户端权威，服务器端瞬移被客户端

- 若覆盖生效 → 走 ChoosePlayerStart 最远点

实测：新车落在 **(-1800, 5000)**，远离主机车（3680cm）→ **Bug2 修复确认生效**。

计划书写「计分：`APlayerState::Kills`（引擎自带复制）」——**UE5 里不存在这个字段**。
核对 5.8 源码：`APlayerState` 只剩 `Score`(float)，`Kills`/`Deaths` 在引擎框架类
（PlayerState / GameStateBase）里**全都搜不到**（那是 UE4 之前的记忆）。
所以必须自定义 PlayerState 自己加字段 + 自己写复制。

# 第三增量：修掉两个遗留小问题 + 一个重要的验证工具坑

## 修复 1：阵亡镜头掉到原点朝天（已修 + 截图验证）

根因在引擎（PlayerController.cpp:994）：
```cpp
void APlayerController::CalcCamera(float DeltaTime, FMinimalViewInfo& OutResult)
{
    OutResult.Location = GetFocalLocation();   // 无 Pawn 时 = PC 自身位置
    OutResult.Rotation = GetControlRotation(); // PC 的操控朝向
}
```
Pawn 销毁后 PC 既没被移动过、操控朝向也不是坦克朝向 → 镜头跑到原点朝天（截图实测：整屏只剩天空）。

**坑**：`AController::SetActorLocation` 是 **private**，外部挪不动 PC（第一版就卡在这，编译报 C2248）。

**解法**：新增 `TankPlayerController`，覆盖 `CalcCamera` 真正读的那两个函数
（`GetFocalLocation` / `GetControlRotation`），阵亡期间返回"最后的观战位姿"；
`OnPossess` 时清掉，自动交还引擎默认。GameMode 里 `PlayerControllerClass` 指过去。
`TankPawn::HandleDeath` 通过 `Client` RPC 把位姿送过去（主机走本地执行，不依赖引擎对本地 Client RPC 的短路）。

镜头位置取 **残骸后上方**（退后 900 / 抬高 350）：第一版放在残骸正上方，镜头正好卡在爆炸球内部。
已验证：截图显示残骸、爆炸球、道路、远处坦克、以及"坦克被击毁 / 正在重生…"提示都在画面里。

## 修复 2：`MulticastDeathFX` 爆炸球不消失（已修 + A/B 截图验证）

`DrawDebugSphere(..., bPersistentLines = **true**, LifeTime = 2.0f, ...)`——
`bPersistentLines=true` 的语义是"持久线，直到 FlushPersistentDebugLines 才清"，**LifeTime 不生效**，
所以爆炸球一直挂在残骸上（刚重生的车看起来像套在爆炸里）。
改成 `false` + `LifeTime=2.0f`（与 `ATankProjectile::OnHit` 的写法一致）。
A/B 截图验证：击杀瞬间球在场 → 12s 后完全消失。

## 重要工具坑：**从 Python 桥调截图会让编辑器崩溃**（务必记住）

**症状**：`EXCEPTION_ACCESS_VIOLATION`，callstack 最内层是 `python311.dll` →
`PythonScriptPlugin` → `CoreUObject` → `Engine`（即文件桥的 tick → exec 路径，**没有任何游戏代码帧**）。
故障地址形如 `0x00007465736c6f18`——那串字节是 ASCII `"teslo"`，即**把字符串当指针解引用**，
典型的悬空引用。

**已确认的事实**：
- 崩溃会话全部包含「从桥里调 `unreal.AutomationLibrary.take_high_res_screenshot`」
- 无截图的长会话（击杀 + 70s / 击杀主机 + 60s）**都不崩**
- 复刻「主机击杀 + 同调用截图 ×3」两次都在约 50~65s 后崩
- 崩溃与我的 C++ 改动无关：三条新代码路径（非主机击杀 / 主机死亡镜头 / 纯截图）单独跑都活过 60~75s

**部分缓解（不保证）**：`take_high_res_screenshot` 是 **latent** Blueprint action，
返回的代理对象若被丢弃会被 GC、回调指针悬空。把代理存进模块级列表
（`Content/Python/tank_shot.py`，模块在 `sys.modules` 里长期存活）后，
一次 75s 的复刻测试存活，但**下一次同样写法仍在 ~65s 崩溃**——所以只是降低概率。

**结论与用法**：
- 这是**验证工具链的坑，不是游戏代码缺陷**
- 截图只当开发期辅助手段：**截完就把要保存的东西存好**，并预期编辑器可能崩溃，崩了重启即可
  （PIE 状态是临时的，不会丢资产）
- 所有截图脚本已统一改用 `import tank_shot; tank_shot.shot("x.png")`
- 另注：`HighResShot` / `Shot` 控制台命令走 `GEditor` 的 active viewport，
  多窗口 PIE 下**不产生文件**，所以指望不上它替代

## 改动

**出生环**：圆心 (0, 4600)、半径 2800、8 点按 22.5° 起偏均布、全部朝圆心。
复用原有 3 个 PlayerStart + 新建 5 个。

**掩体**：中央矮墙 + 四角方块（`Engine/BasicShapes/Cube` + `BasicShapeMaterial`，灰盒）。

## 自己抓到的设计缺陷（截图看出来的）
